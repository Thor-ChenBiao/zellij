# Agent Control Plane 进度 - 2026-04-03

## 摘要

今天的重点是把基于 Zellij 的 agent control plane 从“命令面和元数据骨架”推进到“能看到真实 pane 活动，并且能生成 / 记录 / 回注 review request-feedback”的阶段。

这次的范围仍然是有意控制过的：先把 bridge 真正接到 Zellij pane 边界，把 `view events` / `view code` 变成有真实内容可看的东西；reviewer 自动闭环暂时不一次性做完。

- `zellij review feedback [id]`

已经实现的行为：

- 不带 `id` 会创建新的共享房间 ID 并打印出来
- 带 `id` 时，如果存在就加入；不存在就创建
- 房间元数据会持久化到 Zellij 缓存目录
- 每个房间成员都会记录参与者元数据
- reviewer 启动时会写入固定的 bootstrap 身份提示
- reviewer 启动时会写入固定的 review 消息模板
- `view events` 和 `view code` 会跟随房间自己的流文件
- `zellij-server` 现在会把真实 pane 活动写进房间流
- `view events` 现在能看到真实输入事件，以及从 PTY 输出里启发式提取的 `Bash(...)` / `Write(...)` / `Edit(...)` 等工具轨迹
- `view code` 现在能看到两类真实数据：
  - 从 PTY 输出里提取出的文件线索
  - pane viewport 变化后的代码快照
- `zellij review request [id]` 现在能基于真实 room 流生成结构化 request bundle
- request bundle 会汇总：
  - 最近变更文件
  - 最近 Bash 命令
  - 最近输出摘要
  - 最近 pane 代码快照
- `zellij review feedback [id]` 现在能从 `ACP_REVIEW_RESPONSE_V1` block 记录结构化 reviewer 反馈
- 如果 feedback 标记 `should_send: true`，系统会准备一份发回 driver 的 envelope 文本，落到房间 inbox
- 如果房间里能从真实流里解析出目标 pane，`zellij review feedback [id]` 会直接把 envelope paste 回 driver pane，并补一个 Enter
- 如果当前没法可靠定位目标 pane，envelope 会保留在房间 inbox，并在事件流里记成 waiting 状态
- request 生成时会把推断出的 `target_pane_id` 回写到 driver endpoint 元数据里
- feedback 回注时会优先读 endpoint 上持久化的 `bound_pane_id`，降低每次都靠最近事件现猜的概率

## 还没做的部分

当前实现还只是基础层。

还缺：

- reviewer 自动触发并自动回写 driver pane 的完整闭环
- reviewer request 的自动触发时机判断
- `Esc` 驱动的暂停/接管机制
- 局域网 / WebSocket transport
- 比纯日志跟随更丰富的人类观察界面
- provider 进程的自动起 pane 和更强的 endpoint 绑定

## 已经锁定的设计点

当前交互模型已经收敛成一个很简单的版本：

- 用户只需要关心一个共享 `id`
- 运行时 `endpoint_id` 保持内部化
- 不同 provider 的差异通过 Zellij pane 归一
- reviewer 被当成一等参与者，而不是特殊 sidecar

这和 [README.md](/Users/chenbiao/zellij/docs/agent-control-plane/README.md) 中的设计方向一致。
